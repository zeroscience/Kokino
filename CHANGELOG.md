# Changelog

All notable changes to Kokino Forensic Toolkit are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Disk images stored on the evidence (E01 with its segments, VHD, VHDX, VMDK with its extents, ISO, split and plain raw disks) are listed on the evidence summary; "Extract as evidence" copies all of an image's files into the case (checked against the bytes read), records them in the audit log with their hashes and where they came from, and adds and analyzes the image as evidence of its own.
- Triage collections: a ZIP added as evidence is read as a file system (central directory, ZIP64, NTFS and Unix time fields, Velociraptor's escaped names), so Velociraptor offline collections and KAPE ZIP output can be examined as they are, their hash being the collector's. On any volume where a collected drive sits below a folder (KAPE's C, Velociraptor's uploads/auto/C:), Windows and Linux artifacts, browser history and email are read with the paths they had on the drive; checks that need a whole volume are not made from a collection.
- Volume Shadow Copies: on every NTFS volume the shadow copy stores are found (catalog, block lists with full, overlay and forwarded blocks) and each snapshot is rebuilt from the copied blocks and the live volume, then read as a volume of its own ("Shadow copy N of volume X, created ..."), with all the analysis a volume gets: files as they were, deleted files, artifacts, timeline, search. Checked against the published results for dfvfs' vss.raw (store IDs, creation times, the files each snapshot holds). Shadow copies are not carved and show no image offsets, since their bytes are not at one place in the image.
- BitLocker (Windows 7 and later, BitLocker To Go): the summary lists each encrypted volume with its method (AES-128 or AES-256, CBC with or without the Elephant diffuser, XTS), drive label, volume ID, date and key protectors. Unlock with the password or the 48-digit recovery password: the volume key found is kept with the case (keys folder, never the password, never sent to the browser), the unlock is recorded in the audit log (failed attempts too), and the decrypted volume is added as a volume of its own and analyzed like any other. Volumes with protection suspended (clear key) are read without asking. `kokino analyze`, `files` and `carve` take `--bitlocker-password` and `--recovery-password` ("-" asks). Checked on dfvfs' BitLocker To Go image (AES-128 with the diffuser): every file decrypts to the documented content. Windows Vista volumes, TPM and startup key protectors are not read; decrypted volumes are not carved yet.
- Fuzz targets `zip` (the ZIP reader and nested image detection, 5,383,514 inputs), `vss` (shadow copy stores and snapshot reads, 9,887,067) and `bde` (BitLocker metadata, protectors and the decrypting reader, 1,891,137). They found 5 problems, all fixed before release and kept as regression inputs. Totals: 584,319,572 inputs over 34 targets, 34 problems found and fixed (SECURITY.md).

### Fixed
- Found by fuzzing before release: ZIP collections (a Velociraptor-escaped name next to a multi-byte character stopped the analysis; a damaged ZIP could claim sizes that exhausted memory), shadow copies (offsets near 2^64 overflowed; a catalog listing thousands of stores overflowed the stack) and BitLocker (an offset near 2^64 overflowed).

## [1.3.0] - 2026-11-09

Email, exports and older systems: mbox and .eml mail, every list as CSV or JSON, registry transaction logs, text of legacy Office files, Windows XP event logs, Internet Explorer cookies and compressed journald fields.

### Added
- Exports of every list as CSV or JSON: files (with $SI and $FN times and, after hash analysis, MD5, SHA-1 and SHA-256), the timeline, anti-forensics indicators, web visits, downloads, searches and the Internet Explorer cache, Windows programs run, files opened, ShellBags, the change journal, autostart entries, scheduled tasks, installed programs, USB devices, networks, accounts, notable events, deleted registry keys and values and SRUM, the Linux shell history, logons, events, packages and persistence, and carved files and Internet Explorer records. Times are ISO 8601 UTC and both formats have the same columns; CSV has a UTF-8 byte-order mark and puts an apostrophe before a cell that starts like a spreadsheet formula, JSON keeps every value exactly. Each export is saved in the case's exports folder and its SHA-256 recorded in the case audit log. In the GUI: "Export lists" on the evidence summary (every list with its row count), and CSV and JSON buttons on the Timeline, Web activity and Carved files pages; reviewers cannot export, as with files. On the command line: `kokino export <case folder> [evidence] [list|all] [--fs N] [--format csv|json]`.
- Text of legacy Office files for full-text search (new module `kokino_analysis::oletext`): Word 97-2003 through the piece table (8-bit and UTF-16 pieces, field codes dropped and field results kept), Excel 97-2003 shared strings (including strings split over CONTINUE records), older LABEL cells and sheet names, PowerPoint 97-2003 text atoms, Outlook .msg text properties (subject, body, sender, recipients, attachment names), and the document properties of any OLE file (title, subject, author, keywords, comments, last saved by). RTF text, with \'hh and \u escapes decoded and font tables, pictures and other non-text groups skipped. Live, deleted and carved files alike; encrypted Word and Excel files are reported.
- Registry transaction logs (new module `kokino_artifacts::reglog`): a hive that was not cleanly saved gets the changes still in its .LOG1 and .LOG2 (.LOG on Windows XP) applied in memory before it is read, as Windows would on its next start. Both formats: Windows 8.1 and later (log entries checked with their Marvin32 checksums and applied in sequence order across both logs, the replay stopping at the first damaged or missing entry) and Windows XP to 8 (dirty sector bitmap). A damaged log is not used, and the Sources list says what was applied or why not. `kokino artifact` applies logs found next to a hive and reports it. Checked against Windows' own recovery on public test hives (VALIDATION.md): identical for the new format; for the old format identical apart from two fields Windows rewrites whenever it loads a hive.
- Fuzz target `reglog` (58,565,421 inputs) and a further round of `doc` with Word, Excel, PowerPoint, Outlook and RTF seeds (37,498,697 inputs): no problems found. Totals: 475,652,711 inputs over 28 targets, 29 problems found and fixed (SECURITY.md).
- Test image `disk-win.img`: alice's UsrClass.dat is left as Windows leaves a hive it has not flushed (the sector with the ShellBags root key only in UsrClass.dat.LOG1), so the ShellBags tests also test the log replay.

- Legacy Windows event logs (.evt, Windows NT to Server 2003; new module `kokino_artifacts::evt`): SecEvent.Evt, SysEvent.Evt and AppEvent.Evt are read like EVTX, including records left in the unused part of the circular log and records that wrap around its end. Security events of those Windows versions get the field names Vista and later use, so they appear under Events with their user, logon type and address and count for the indicators: logons (528, 540), failed logons (529 to 539), log cleared (517), process started (592, also under Programs run), accounts created, enabled, disabled, deleted and reset (624 to 630, 644), group changes (632, 636, 660), service installed (601), audit policy (612) and time changed (520). Windows XP profiles under Documents and Settings (NTUSER.DAT, UsrClass.dat, Recent shortcuts) and a Windows 2000 \WINNT folder are found. `kokino artifact` reads .evt files.
- Internet Explorer cookies: the Cookies folders' index.dat joined with each site's cookie text file (name, value, site and path, created, expires, flags, and from the index when the site's cookies were last used). Cookie files the index no longer lists and index entries whose file is gone are listed and marked. New "IE cookies" list in Web activity, CSV/JSON export. On Digital Detective's practice case: 222 cookies from 87 sites, and two deleted index entries whose cookie files are gone (VALIDATION.md).
- systemd journal: fields journald stored compressed are decoded (XZ and zstd with the pure-Rust lzma-rs and ruzstd crates, LZ4 by Kokino itself), instead of being counted and skipped.
- Email (new module `kokino_analysis::mail`): mbox mailboxes (Thunderbird and SeaMonkey mail folders, /var/mail and /var/spool/mail, .mbox and .mbx files) and .eml files, live and deleted. Every message with its date, sender, recipients, subject, attachments and the first words of its text; headers in encoded words, bodies in quoted-printable or base64 and in their character set, HTML without markup, attached messages and nested multiparts. Messages Thunderbird deleted but has not yet removed from the file (X-Mozilla-Status 0x0008) are marked. New Email page (mailboxes, filter, message text, all headers, attachments with audited export), email on the Timeline (source MAIL), a line in the impact summary, CSV/JSON export, and message text and document attachments in the full-text index.
- Fuzz targets `evt` (30,689,834 inputs), `mail` (7,542,816) and `journalz` (journald's XZ, LZ4 and zstd, 45,374,291), and a further round of `linuxlogs` with a journal holding compressed fields (7,898,202): no problems found. Totals: 567,157,854 inputs over 31 targets, 29 problems found and fixed (SECURITY.md).

### Changed
- Analysis schema 10. Evidence analyzed by an earlier version is offered a re-analysis in the System summary, Web activity and the Email page.
- The anti-forensics rules `evtx_cleared` and `log_cleared_event` cover Windows XP and 2003 too: a SecEvent.Evt no larger than a reset log (64 KiB), and event 517.
- The Windows test image's carving sample `draft.docx` is now built with a fixed time, so the test images are the same every time they are built.
- The carving sample order on the test volume changed (the new log file took free clusters); the carving test was updated.

## [1.2.9] - 2026-11-08

More Windows: scheduled tasks (hidden ones flagged), Internet Explorer history with records recovered from free space, and deleted registry keys and values.

### Added
- Scheduled tasks (new module `kokino_artifacts::task`): every task file under `Windows\System32\Tasks` (author, registration date, account and privilege level, triggers in plain words, what it runs, hidden and disabled flags) joined with the registry's TaskCache (SOFTWARE), which adds when each task was created and last ran, the result of its last run, and a binary copy of its actions for tasks whose file is gone. Shown in a new "Scheduled tasks" card in the System summary (Windows' own tasks behind a toggle), with tasks that are not Windows' own, or run from unusual places, in the autostart list; task registrations and last runs on the Timeline; a table in the case report and lines in the impact summary. Tasks registered without a task file, and task files no longer registered, are marked. Checked on a real Windows 7 SOFTWARE hive (83 tasks, VALIDATION.md).
- Anti-forensics indicator `task_hidden_sd` (25 in total): a task whose TaskCache\Tree key lost its SD value, which hides it from schtasks and the Task Scheduler while it keeps running (the Tarrask technique). Only where the hive's other tasks have an SD value: Windows 7 writes none.
- Deleted registry keys and values (`Hive::deleted` in `kokino_artifacts::registry`): the free space of every hive bin is searched for key and value cells that Windows freed but did not clear. Each deleted key gets the path of the live key it belonged to (through deleted parents too), its last-written time and the values whose cells are still free; values whose data cell is in use again are marked. Older copies of keys that still exist (Windows leaves one when it moves a key) are recognized, and only the values they hold that the live key no longer has are reported, as deleted values of that key; values found on their own are listed without a key. New System summary page "Deleted registry" (filter, only keys that record user activity, details per key), deleted keys on the Timeline (source REG), a table in the case report, a line in the impact summary, and counts (`--full`: every key and value) in `kokino artifact` for a hive. Keys that record user activity (recent documents, the Run box, typed paths and addresses, dialog history, Explorer searches, UserAssist, ShellBags, mounted drives, Office recent files, Run, USB devices, networks, remote desktop, BAM) are named. Transaction logs (.LOG1/.LOG2) are still not applied.
- Anti-forensics indicator `registry_traces_deleted` (26 in total): a whole key that records user activity found deleted, which is what cleaners such as CCleaner do (Windows trims these lists one entry at a time).
- Fuzz target `task` (task XML, the Actions and DynamicInfo blobs, TaskCache in a hive): 19,733,957 inputs, no problems found.
- Test image `disk-win.img` now holds four scheduled tasks: one of Windows' own, one running from C:\Users\Public, one hidden Tarrask-style and one registered without a task file.
- Internet Explorer history (new module `kokino_artifacts::iecache`, the index.dat format of Internet Explorer 4 to 9): the main history, daily and weekly history files, protected-mode (Low) history, the cache (Content.IE5) and IE 9's download list are read into Web activity next to Chrome and Firefox. Visits with page titles and visit counts (local files opened through Explorer appear as `file:` visits), cached files with their cache folder and file name, content type and hits, downloads with source URL, referring page, saved path and bytes received, and search terms from visited search pages. Every 128-byte block is checked, so deleted entries still inside the file are listed too, marked "deleted entry"; LEAK entries (deleted, but the cached file was still in use) are marked. A last visit that the main file repeats from a daily file is shown once. Daily files keep each visit time also in local time, so the source card says what the computer's clock was set to while browsing. New "IE cache" list in Web activity; visits on the Timeline; IE sources in the case report and the impact summary.
- Carving recovers Internet Explorer records from free space: every 128-byte boundary of free clusters and unpartitioned space is checked for a history, cache, cookie, download or redirect record (records keep that alignment when index.dat is deleted), and whole index.dat files are carved as files. New "ie-records" list on the Carved files page; `kokino carve` lists the records after the files.
- `kokino artifact` reads an exported index.dat (counts by record type, deleted records, cache folders; `--full` for every record).
- Validation on Digital Detective's practice files (VALIDATION.md): all 16 index.dat files of the Windows 7 laptop read, and the formatted E01 of the same case gives back all 15 index.dat files whole and all 5,920 of their records from free space, the same counts as the live files. That check found and fixed two problems before release (records inside a carved file longer than the 1 MiB read window were skipped; the clock offset was truncated to UTC+02:45 instead of rounded to UTC+03:00).
- Fuzz target `iecache` (index.dat, the conversion of each kind of file, and records read from free space at every 128-byte boundary): 21,653,615 inputs; it found one problem before release (a record cut off by the end of the file, with its data offset past the bytes that exist, panicked), fixed and kept as a regression input. A further round of `registry`, which now also recovers deleted keys and values: 18,700,883 inputs, no problems found. Totals: 379,588,593 inputs over 27 targets, 29 problems found and fixed (SECURITY.md).
- Test image `disk-win.img` now holds deleted registry keys: in alice's NTUSER.DAT a TypedURLs key deleted with its Internet Explorer parent, the SDelete EULA key deleted with its Sysinternals parent, and an older copy of RunMRU that still holds an entry removed since; in her UsrClass.dat a value on its own.
- Test image `disk-win.img` now holds Internet Explorer files for alice (a daily history with a search, a visit seen again in the main file and a deleted entry; the main history with a local file opened; the cache with a LEAK entry; a download) and, after the volume, a deleted index.dat and two loose records for carving.

### Changed
- Analysis schema 9 (7: scheduled tasks; 8: Internet Explorer; 9: deleted registry keys). NTFS evidence analyzed by an earlier version is offered a re-analysis in the System summary and in Web activity, which name what is missing.
- Carving results schema 2. Results from an earlier version still open; the Carved files page suggests carving again to look for Internet Explorer records.
- The `browser_history_cleared` indicator counts only Internet Explorer's main history files: cache and download lists hold no visits, and Windows deletes daily and weekly history files itself as they age. Searches such as "clear ie history" now count for `antiforensic_web`.
- The server test of session expiry no longer fails on a computer that has been up for less than the idle timeout (it could not move a time back past the system's start).
- The carving samples `memo.doc` and `security.evtx-chunk` moved from the test volume's free clusters to the unpartitioned space after it, to make room for the task files, the index.dat files and the larger SOFTWARE hive.

## [1.2.8] - 2026-11-05

Deeper NTFS and Windows: the change journal, names of deleted files from folder index slack and $LogFile, ShellBags, BAM/DAM and SRUM with Kokino's own ESE database reader.

### Added
- NTFS: names of deleted files whose MFT record was reused, recovered from folder index slack ($I30), the indexes of deleted folders, and $LogFile (which records every index change with the entry). Each is listed as a deleted, name-only entry with its $FILE_NAME times and size, the MFT record it had and a note saying where it was found and what that record holds now; earlier names of renamed or moved files are listed the same way. They have no content (reads say so) and are skipped by hashing. On the NIST CFReDS NTFS images the deleted files listed now match NIST's counts closely (case 08 exactly, VALIDATION.md); the missing names were mostly in $LogFile, not in index slack as VALIDATION.md had assumed. Hard links are recognized as second names of the same record.
- NTFS change journal ($Extend\$UsnJrnl:$J, record versions 2 and 3, and $Max): every record read (sparse parts skipped), records of one round of changes combined into one change (created, data written, renamed with the old name, deleted, ...), paths rebuilt from today's folders or, for folders that are gone, from the journal itself, and each change linked to the file on the volume when its MFT reference and name match. New System summary page "Change journal" (filter by kind and path, paged), a journal summary on the overview (period covered, counts, when the journal was created), a "Change journal" section in the file details, and created, deleted and renamed files on the Timeline (source USN). Up to 250,000 changes are kept (the newest); the summary says when older ones were dropped.
- ShellBags: every folder a user opened in Explorer, from UsrClass.dat (Windows 7 and later) and NTUSER.DAT (BagMRU and ShellNoRoam), with full paths rebuilt from the shell items (drives, folders with long names, network shares, ZIP folders, known folders, URIs, delegate items), last opened time, the folder's own times and MFT reference, and a link to the folder when it is on this volume. New System summary page "Folders (ShellBags)"; opened folders on the Timeline.
- SRUM (System Resource Usage Monitor, `Windows\System32\sru\SRUDB.dat`): per program and user, hour by hour, bytes sent and received over which network and interface, disk bytes read and written and processor time, for the last 30 to 60 days, and network connections with their start and length. Program paths, services and user SIDs are resolved through SruDbIdMapTable and the accounts; Wi-Fi networks by name through WlanSvc's profile index and the profile XML files. New System summary page "Network use (SRUM)" (programs by data sent, each program's hours, connections), hours in which a program sent 100 MiB or more and connections on the Timeline, the top senders in the summary and the case report. A database that was not cleanly closed is reported (its newest hours may be only in the transaction logs, which are not read).
- ESE database reader (new module `kokino_artifacts::ese`, "Jet Blue", used by SRUM and later by other Windows databases): file header and state, 2 to 32 KiB pages with both page header and tag layouts, B+ trees, the catalog, fixed, variable, tagged, multi-valued and long values, and the column compression of Windows 8 and later (7-bit text and XPRESS). Tested on databases written by Windows' own esent.dll (`scripts/make_srum_fixture.py`, 4 KiB and 32 KiB pages, and a tree of three levels), and against a real Windows 10 22H2 SRUDB.dat: all 310,255 rows of its 16 tables, 2,800,979 values, read the same as through esent.dll (VALIDATION.md). That check found and fixed two problems before release: branch pages above the parents of leaves were not followed (Windows marks them with neither page flag), so large tables such as SRUM's id map read as empty; and UTF-16 text in columns declared as ANSI was cut after its first character. SRUM program ids of the form `!!<file>!<date>!...` are shown by their file name.
- BAM and DAM (SYSTEM hive, Windows 10 1709 and later): the last run of each program per user, under "Programs run" (sources BAM and DAM) and on the Timeline; SIDs are shown as account names, and a wiping tool found there counts for `tool_execution_record`.
- Two anti-forensics indicators (24 in total): `usn_wipe_rename` (the change journal shows files renamed AAAA.AAA to ZZZZ.ZZZ, SDelete's pattern; the journal keeps the original names) and `usn_journal_recreated` (the journal was created long after the volume, as when it is deleted and recreated).
- Fuzz targets `indx` (folder index records and $LogFile pages), `usn`, `shellbags` and `ese` (with SRUM on top), and more rounds of `ntfs` (now that it reads indexes and $LogFile) and `registry`: 87,410,557 inputs, no problems found. Totals: 319,500,138 inputs over 25 targets (SECURITY.md).
- Test image `disk-win.img` now also holds UsrClass.dat with ShellBags, a change journal, BAM and DAM entries, a SRUM database and a Wi-Fi profile (`scripts/make_win_fixture.py`); `scripts/validate_cfreds.py` counts names on NTFS too and can run one file system.

### Changed
- An NTFS record that cannot be parsed now gets its name back from its folder's index when the index still lists it, with a note pointing at the unreadable record (the `testfs1` fixture has one, a record split over two MFT runs).
- Hashing (and `kokino files`) skip name-only entries, which have no content.
- Analysis schema 6. On NTFS evidence analyzed by an earlier version, the System summary says that the change journal, ShellBags, BAM/DAM, SRUM and recovered names are missing until it is analyzed again, with a Re-analyze button.

## [1.2.7] - 2026-11-04

Virtual disks, optical media and Mac disks: VHD, VHDX and VMDK (with snapshots), ISO 9660 and UDF (with multisession history), HFS+ and APFS (with deleted files), and an update check that runs only when asked.

### Added
- Update check, only on request: "Check for updates" on the About page and `kokino version --check` ask GitHub's release list for the latest version and show its notes and SHA-256 checksums, with a link to download. Nothing is downloaded or installed, nothing runs on its own, and every check is recorded in the system audit log (`update.check`). The Privacy page says exactly this.
- Virtual disks (new module `kokino_image::vdisk`): VHD dynamic and differencing (fixed was already read), VHDX dynamic, fixed and differencing (partially present blocks with sector bitmaps), VMDK monolithicFlat, monolithicSparse, streamOptimized (deflate grains, as in OVA exports), split extents (twoGbMaxExtentSparse/Flat), VMFS flat extents and snapshot chains. Parents are found next to the child from the paths it records and checked (VHD unique id, VHDX parent linkage, VMDK parent CID); a mismatch, or a VHDX log that was never applied, is reported in the evidence summary. Evidence cards show the exact kind, for example "VMDK (streamOptimized)" or "VHDX (differencing) (+1 parent)".
- Optical media (new crate `kokino-iso`): ISO 9660 with Rock Ridge (names, owners, modes, times, symbolic links, relocated deep folders, continuation areas) and Joliet; multisession discs, where the newest session is the live tree and files only older sessions list are shown as deleted with their session and content; UDF 1.02 to 2.60 with physical and metadata partitions, file and extended file entries, embedded data, and directory entries marked deleted. Bridge discs are read through UDF unless the ISO side has older sessions. Help page "Optical discs and .iso files".
- macOS file systems (new crate `kokino-mac`): HFS+ and HFSX (catalog, extents overflow and attributes B-trees, hard links, resource forks, allocation bitmap) and APFS (checkpoints, object maps, every unencrypted volume of a container, file-system tree, hard links, symlinks, extended attributes). macOS file compression (decmpfs) decoded: zlib and LZVN, inline or in the resource fork. Deleted files from old HFS+ catalog-node copies in the journal and unused nodes, and from older APFS file-system tree nodes, with their content. Encrypted APFS volumes are reported. Help page "Mac disks (HFS+, APFS)".
- Test images `hfsplus.img` and `apfs.img` made with Apple's own tools on GitHub's macOS runner (`scripts/make_mac_fixture.sh`, workflow "Mac test images"), with macOS's own report of every file as ground truth.
- Test images `iso-rr-joliet.iso`, `iso-udf.iso`, `iso-multisession.iso` from `scripts/make_iso_fixture.py` (mkisofs).
- Test images `vd-*.vhd`, `vd-*.vhdx`, `vd-*.vmdk` from `scripts/make_vdisk_fixture.py` (the disk-fat.img disk in every format, plus a known patch in the differencing and snapshot disks); 7-Zip reads the VHD and VMDK ones back to the same bytes.

- Fuzz targets `vdisk`, `optical` and `mac`: 4.75 million inputs; six problems found and fixed before release (UDF: an overflow on tiny images and two out-of-range reads; HFS+: an overflow and an out-of-range read; APFS: an overflow). Totals: 232,089,581 inputs over 21 targets, 28 problems found and fixed (SECURITY.md).

### Fixed
- Volume list: ext volumes were not marked as supported in the disk layout (only the analysis knew); fixed together with ISO 9660 and UDF detection.

## [1.2.6] - 2026-11-02

Linux: ext2, ext3 and ext4 file systems and Linux system artifacts, validated on the NIST CFReDS ext images and fuzzed.

### Added
- ext2, ext3 and ext4 (new crate `kokino-ext`): every inode, extent trees and indirect block maps, inline data and fast symlinks, directories with deleted names recovered from directory-entry slack, orphaned inodes under $OrphanFiles, block bitmap free space for carving and search. Owner, group, mode, inode number and deletion time are shown in the file details; ext4 times to the nanosecond with creation time. Works through MBR and GPT like the other file systems.
- Recovery of deleted ext3/ext4 files through the journal: ext3 and ext4 clear a deleted file's block map, so Kokino looks for an older copy of its inode-table block in the JBD2 journal and, when the inode there is the same file (same generation) with its block map, reads the content through it. Such files show "Recovered from the journal (transaction N)"; the summary counts deleted files with nothing left to recover (carving may still find them).
- Linux system summary (`kokino_analysis::linux`, System summary page): computer (os-release, hostname, time zone, machine id, kernels, boot and shutdown), accounts (passwd, shadow state without hashes, groups, lastlog; second uid 0 accounts, passwordless and system accounts with a shell flagged), logons, failures and reboots (wtmp, btmp, auth.log or secure, journald), shell histories (bash with HISTTIMEFORMAT, zsh, fish, python, mysql, psql, sqlite) with destructive commands flagged, sudo and account changes, packages (dpkg status, dpkg.log, apt history with who installed what, dnf/yum logs, apk, pacman), persistence (cron, systemd units, rc.local, SSH authorized keys with fingerprints and forced commands, sudoers NOPASSWD, ld.so.preload, shell startup lines), USB storage from kernel messages, NetworkManager connections, DHCP leases, SSH known hosts and /etc/hosts entries. Rotated and gzipped logs are read.
- Time zones from the image: /etc/localtime (TZif, with the POSIX rule for later years) converts classic syslog lines, which carry local time and no year; the year is counted back from the log file's modification time and such events are marked.
- systemd journal reader: entry objects with MESSAGE, SYSLOG_IDENTIFIER, _COMM, _PID, _HOSTNAME and more, regular and compact files; compressed fields are counted, not read.
- Linux events on the timeline (commands with times, packages, logons, USB, networks) and inode deletion times as DEL events. The timeline's source filter reads System instead of Windows on non-NTFS volumes.
- Four anti-forensics indicators for Linux: destructive commands in shell, apt or sudo history; shell history emptied or linked to /dev/null; wtmp or auth.log emptied; /etc/ld.so.preload in use.
- Test fixtures `ext2.img`, `ext3.img`, `ext4.img` and `linux-server.img` from `scripts/make_ext_fixture.py` (pure Python, invented data), cross-checked with 7-Zip's ext reader.
- Fuzz targets `ext` (the ext reader) and `linuxlogs` (journal, wtmp, syslog, TZif, apt, DHCP and dpkg parsers).
- Help wiki page "Linux disks (ext2, ext3, ext4)", file system rows on the Cases and evidence page, ext in the carving and search descriptions.
- Validation against the 22 NIST CFReDS ext images (VALIDATION.md): 962 of 965 tagged deleted files complete, 302 recovered through the journal, 2,782 deleted names listed. `scripts/validate_cfreds.py` handles ext and counts deleted names without content.
- Deleted folders on ext3 and ext4: when the folder's block map is cleared, Kokino searches the free blocks of its block group for the directory block that names it, so the files in it keep their names.

### Changed
- New project description in the README, the About page and on GitHub.
- Analysis schema 5 (`FsEntry::unix`, `FsAnalysis::linux`). Evidence analyzed before keeps working; re-analyze to get the new fields.

### Fixed
- System summary: the heading said "Registry, event logs ... of this Windows volume" on every volume; it now describes what is read on NTFS, ext and FAT, and evidence analyzed before the Linux reader offers a re-analysis.
- ext reader (found by the NIST validation before release): ext2 deleted names whose inode number the kernel erased were dropped; deleted ext2 folders (size set to 0 by rmdir) and orphaned folders were not entered; blocks of large indexed folders whose files were all deleted were skipped as index blocks; old copies of names left behind by index splits were listed as deleted files.
- ext reader (found by fuzzing before release): a superblock claiming millions of block groups made the block bitmap buffer reserve hundreds of megabytes from an 83 KB image. Group descriptors and the bitmap are now bounded by what the image holds.
- Linux log parsers (found by fuzzing before release): integer overflows in POSIX time zone rules and in systemd journal object offsets and sizes. Fuzzing now totals 227,335,973 inputs over 18 targets, 22 problems found and fixed (SECURITY.md).

### Security
- Parser bugs found by fuzzing and fixed (crafted evidence could stop or slow a job or exhaust memory; none allowed code execution or wrote to evidence):
  - NTFS: the declared MFT size was trusted (hang, runaway memory); a data-run iterator that repeats its error looped for ever; a boot sector shorter than 512 bytes made the `ntfs` crate panic; read buffers and the free-space bitmap were sized by declared lengths.
  - FAT and exFAT: the boot sector's cluster count sized the in-memory FAT (16 GB from a 2.6 MB image); exFAT sector and cluster shifts were not checked (clusters up to 128 GiB); three unchecked multiplications.
  - Jump Lists (OLE compound files): repeated DIFAT sectors and looping chains (over 500 MiB from a 3 KB file).
  - Registry: a key listed under itself made the tree walk exponential.
  - E01: unchecked chunk geometry arithmetic.
  - JPEG: DC size from the file's Huffman table not checked, coefficient overflow, a frame header claiming 1.2 gigapixels kept the decoder busy on padding (now stops 1 KiB past the data), and a scan naming a component a later frame header removed crashed it.
  - PDF text extraction and PDF carving: two slicing panics.
- Browser history: SQLite databases from evidence are opened in defensive mode with `trusted_schema=OFF`, cell size checks, no memory mapping and a time limit; a database that defines `urls` (or another table Kokino reads) as a view is refused. A crafted History file could otherwise hang the ingest for ever (proof of concept made). Hash set imports from SQLite get the same protection.
- Evidence paths inside the cases directory are refused: an examiner could otherwise add another case's files, the account file or the TLS key as "evidence" and read it in the hex view.
- A panic in a background job now ends the job as failed (with a request to report it) instead of leaving it "running" and blocking Delete case.
- Reports (HTML from the API) are served with a sandboxing Content-Security-Policy and no scripts.
- `#![forbid(unsafe_code)]` in every Kokino crate: the compiler now refuses unsafe Rust anywhere in the product.
