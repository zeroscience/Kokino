# Changelog

All notable changes to Kokino Forensic Toolkit are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- ext2, ext3 and ext4 (new crate `kokino-ext`): every inode, extent trees and indirect block maps, inline data and fast symlinks, directories with deleted names recovered from directory-entry slack, orphaned inodes under $OrphanFiles, block bitmap free space for carving and search. Owner, group, mode, inode number and deletion time are shown in the file details; ext4 times to the nanosecond with creation time. Works through MBR and GPT like the other file systems.
- Recovery of deleted ext3/ext4 files through the journal: ext3 and ext4 clear a deleted file's block map, so Kokino looks for an older copy of its inode-table block in the JBD2 journal and, when the inode there is the same file (same generation) with its block map, reads the content through it. Such files show "Recovered from the journal (transaction N)"; the summary counts deleted files with nothing left to recover (carving may still find them).
- Linux system summary (`kokino_analysis::linux`, System summary page): computer (os-release, hostname, time zone, machine id, kernels, boot and shutdown), accounts (passwd, shadow state without hashes, groups, lastlog; second uid 0 accounts, passwordless and system accounts with a shell flagged), logons, failures and reboots (wtmp, btmp, auth.log or secure, journald), shell histories (bash with HISTTIMEFORMAT, zsh, fish, python, mysql, psql, sqlite) with destructive commands flagged, sudo and account changes, packages (dpkg status, dpkg.log, apt history with who installed what, dnf/yum logs, apk, pacman), persistence (cron, systemd units, rc.local, SSH authorized keys with fingerprints and forced commands, sudoers NOPASSWD, ld.so.preload, shell startup lines), USB storage from kernel messages, NetworkManager connections, DHCP leases, SSH known hosts and /etc/hosts entries. Rotated and gzipped logs are read.
- Time zones from the image: /etc/localtime (TZif, with the POSIX rule for later years) converts classic syslog lines, which carry local time and no year; the year is counted back from the log file's modification time and such events are marked.
- systemd journal reader: entry objects with MESSAGE, SYSLOG_IDENTIFIER, _COMM, _PID, _HOSTNAME and more, regular and compact files; compressed fields are counted, not read.
- Linux events on the timeline (commands with times, packages, logons, USB, networks) and inode deletion times as DEL events. The timeline's source filter reads System instead of Windows on non-NTFS volumes.
- Four anti-forensics indicators for Linux: destructive commands in shell, apt or sudo history; shell history emptied or linked to /dev/null; wtmp or auth.log emptied; /etc/ld.so.preload in use.
- Test fixtures `ext2.img`, `ext3.img`, `ext4.img` and `linux-server.img` from `scripts/make_ext_fixture.py` (pure Python, invented data), cross-checked with 7-Zip's ext reader.
- Fuzz targets `ext` (the ext reader) and `linuxlogs` (journal, wtmp, syslog, TZif, apt, DHCP and dpkg parsers).
- Help wiki page "Linux disks (ext2, ext3, ext4)", file system rows on the Cases and evidence page, ext in the carving and search descriptions.
- Validation against the 22 NIST CFReDS ext images (VALIDATION.md): 962 of 965 tagged deleted files complete, 302 recovered through the journal, 2,782 deleted names listed. `scripts/validate_cfreds.py` handles ext and counts deleted names without content.
- Deleted folders on ext3 and ext4: when the folder's block map is cleared, Kokino searches the free blocks of its block group for the directory block that names it, so the files in it keep their names.

### Changed
- Analysis schema 5 (`FsEntry::unix`, `FsAnalysis::linux`). Evidence analyzed before keeps working; re-analyze to get the new fields.

### Fixed
- ext reader (found by the NIST validation before release): ext2 deleted names whose inode number the kernel erased were dropped; deleted ext2 folders (size set to 0 by rmdir) and orphaned folders were not entered; blocks of large indexed folders whose files were all deleted were skipped as index blocks; old copies of names left behind by index splits were listed as deleted files.
- ext reader (found by fuzzing before release): a superblock claiming millions of block groups made the block bitmap buffer reserve hundreds of megabytes from an 83 KB image. Group descriptors and the bitmap are now bounded by what the image holds.
- Linux log parsers (found by fuzzing before release): integer overflows in POSIX time zone rules and in systemd journal object offsets and sizes. Fuzzing now totals 227,335,973 inputs over 18 targets, 22 problems found and fixed (SECURITY.md).

## [1.2.5] - 2026-11-01

First public release.

### Added
- ROADMAP.md: what 1.2.5 does and what comes next (ext4 and Linux artifacts, VHDX, VMDK, Ex01, ISO 9660, UDF, then HFS+, APFS, BitLocker, VSS and more), linked from the README.
- Installable packages built by GitHub Actions (`.github/workflows/release.yml`) when a release is published: Windows MSI (Program Files, Start menu entry that starts Kokino and opens the browser, `kokino` on the PATH) and zip, Linux tar.gz and .deb (with a desktop entry), macOS universal DMG (Intel and Apple Silicon, with a "Start Kokino" launcher), and SHA256SUMS.txt. Not code-signed yet.
- `kokino purge`: removes everything Kokino stored on the machine (cases, accounts, audit logs, hash sets, TLS key, deleted cases) after showing what and how much and asking for DELETE ALL. Evidence images and unrelated files are never touched.
- Error log: every error shown as a notification is kept in the browser (the last 100, newest first). A red button in the top bar shows how many are unread; it opens the list with each error's time and full text and a Copy button, and can be cleared.
- Hash sets: NSRL RDS v3 releases published as SQL files (`.sql`, full and delta) are imported by column name: only the md5, sha1 and sha256 columns are taken. Before, such a file fell through to the plain-list reader, which also took NSRL's internal `key_hash` values as SHA-256 file hashes. The RDS 2026.09 modern delta (5.2 million rows, 1.45 million distinct files) imports in about 2 minutes into a 134 MB set.
- Hash sets: when NIST's `signatures.txt` sits next to the file being imported, the file's SHA-256 must match it, or the import stops ("incomplete or altered, for example an unzip that stopped early"); a match is recorded and shown on the Hash sets page. A SQL file that ends in the middle of a statement is refused as cut short.
- Validation against public test images (VALIDATION.md, wiki section Validation): Digital Corpora nps-2009-canon2 and nps-2009-ntfs1, and NIST CFReDS deleted file recovery (61 FAT, exFAT and NTFS images, checked block by block with `scripts/validate_cfreds.py`). 3,048 of 3,323 deleted test files complete, 99.8% of blocks right (exFAT and NTFS 100%). The About page credits Digital Corpora and NIST CFReDS.
- `kokino files <image> [--json] [--extract DIR]`: every file, live and deleted, with MD5, SHA-1 and SHA-256 and Kokino's recovery note; `--extract` writes them out.
- `kokino carve <image> [--json]`: carve from the command line; each carved file with offset, length and hashes.
- NTFS compression: LZNT1-compressed files (compressed folders, compressed system files) are decompressed, including files split over an attribute list and deleted ones. Checked against Windows' own compressor and the nps-2009-ntfs1 image; fuzzed (new `lznt1` target).
- File details mark EFS-encrypted files: content, hashes and text are of the ciphertext.
- Parser fuzzing (`crates/kokino-fuzz`): a mutation fuzzer on stable Rust with 16 targets covering every parser that reads evidence (partition tables, NTFS, FAT and exFAT, E01, registry, event logs, LNK, Prefetch, Jump Lists, LZXPRESS, document text, pictures, carving, browser databases, strings). Panics, integer overflow, stack overflow on a 2 MiB stack, memory over budget and inputs slower than 20 s count as failures; every failing input is reproducible and replayed by `cargo test`. Three rounds over all targets and follow-up rounds (pictures, NTFS compression, file system walkers) ran 197 million inputs and found 18 distinct problems, all fixed. Results and method in SECURITY.md and the wiki (Security and fuzzing).
- SECURITY.md: how to report a vulnerability (lab@zeroscience.mk), threat model, fuzzing results, server review, limits of the testing.
- GitHub page: README with the Kokino logo, build, release, license, platform and repository badges, and a 12-picture screenshot gallery (placeholders in docs/screenshots to replace). Features list brought up to date (hash sets, byte map and strings, case reports, case edit and restore).
- CI workflow (.github/workflows/ci.yml): cargo test on Windows, Linux and macOS for pushes to main (or master) and pull requests.
- Edit case: examiners on a case and admins change its name and description; admins can also hand it to another lead examiner (made an examiner on the case). The case id and folder stay; each change goes to the case audit log with old and new values (`case.update`) and appears in case reports.
- Deleted cases page (admins): cases removed with Delete case, with who deleted them and when, and Restore, which moves the folder back as it was; recorded as `case.restore` in the case and system audit logs. A case whose id is in use again cannot be restored over it.
- Wiki section Logo and artwork: about the painting behind the new logo, with the original Kokino emblem.
- Byte map (after binvis.io): files, carved files and the whole image drawn along a Hilbert curve, colored by byte class (0x00, 0xFF, text, low, high) or entropy; hover for offset and make-up, click to open the place in the hex. In file details, the picture viewer and carved files (Bytes and strings), and Hex (Byte map).
- Strings: printable text with offsets (ASCII, UTF-8 including Cyrillic, UTF-16LE), minimum length, encoding filter and search; binary that only decodes like text is filtered out. First 64 MiB of a file. Same places as the byte map.
- Hash sets and hash analysis:
  - Admins import hash sets (Hash sets page; CLI `kokino hashset import|list|enable|disable|delete`): NSRL RDS v3 (SQLite), NSRL RDS 2.x NSRLFile.txt, CSV with hash columns, plain lists. Kind known good (hide) or known bad (flag). Stored once in `<cases>/.kokino/hashsets`, shared by every case; imports, changes and deletions go to the system audit log with the source file's SHA-256.
  - Hash analysis per evidence item (new tab; also at the end of ingest): MD5, SHA-1 and SHA-256 of every file with content, looked up in the enabled sets. Check again re-matches stored hashes after the sets change without reading the evidence. Case audit entry `evidence.filehash` names the sets used.
  - Explorer: Known bad / Known badges, a Known bad filter and Hide known good. File details show the hashes and matching sets. Case reports list the hash analysis per evidence item and hash-set matches per exhibit.
- Case report for handing over (Bookmarks page, button Case report; CLI `kokino report <case folder>`):
  - Bookmarks (all, or one tag) become numbered exhibits with location, timestamps, size, hashes, automated findings with their caveats, tags and the examiner's note.
  - Each exhibit is read from the evidence again and hashed; the report says whether it still matches the hash taken when it was bookmarked.
  - Pictures are rendered from the evidence bytes, with a bookmarked region outlined and enlarged (new baseline color JPEG decoder); byte ranges and search hits get a hex dump and SHA-256.
  - Also: cover with reference and requester, examiner's summary, exhibit index, evidence with hash verification, chain of custody from the case audit log with the hash-chain state, methods and tools, limitations, sign-off block, optional full audit log appendix.
  - Written as HTML (print to PDF, page numbers on every page) and Word (.docx, generated without extra libraries) into the case exports folder; both SHA-256 values go to the case audit log (`report.case`), and the Case reports list checks each file against them.

- Delete user accounts (admins, under Users; CLI `kokino user delete <name>`), built so the record stays unambiguous:

  - A never-used account (test accounts, typos) is removed completely. A used one loses its password hash and display name and is signed out, but its username stays reserved under "Deleted accounts" and can never be created again, so the audit entries, bookmarks and records that name it keep meaning one person.
  - The account is removed from every case it was assigned to (case audit entry `case.member_removed`), and the deletion is written to the system audit log (`user.delete`, with what it found). Your own account and the last active admin cannot be deleted.

- Photo forensics (new Pictures page per evidence item and a picture viewer):
  - Every JPEG, PNG and BMP of the evidence (live, deleted and carved) is analyzed after analysis and carving, or on demand; results go to `<case>/photos/<eid>.json` (findings only, no copies) and each run to the audit log.
  - Findings, each with an explanation and a caveat: saved by editing software (EXIF, XMP, Adobe and Photoshop segments, comments); EXIF thumbnail shows a different picture (shape check and a 6x6 grid comparison); compressed twice (double JPEG quantization in the DCT coefficient histograms); camera brand in EXIF but standard libjpeg tables; tables that differ from the same camera's other photos in the evidence; data after the end of the image (appended ZIP and the like; phone trailers, motion photos and MPF images listed as normal); least significant bits that look like hidden data in PNG and BMP (chi-square test from the start and from the end of the pixel data, with a control against naturally smooth histograms); GPS position, EXIF changed date differing from the capture date, no EXIF in a camera folder.
  - Kokino's own JPEG parser and baseline Huffman decoder (checked against Pillow on 231 real and re-saved pictures), EXIF reader, PNG decoder (all filters) and BMP reader. libjpeg tables are identified with their exact quality; other tables get an estimate and a fingerprint.
  - Calibration on the 33 photos of a public Canon SD card image and variants made from them: unedited camera photos produce no findings; the thumbnail check caught 79% of cloned regions, all painted areas and all crops with no false alarm; the double-compression threshold (0.20) stays above every single save tested and catches about 62% of re-saves (a camera's near-lossless first save leaves no trace, and the wiki says so); the LSB test found sequential embedding of 10%, 30% and 100% in all 20 photos tried and flagged none of the clean ones, while embedding spread thinly over the whole picture is not detected.
  - Viewer: pixels as stored (no color management or EXIF rotation), zoom and pan, magnifier (2x to 8x, plain, auto-contrast or equalized), error level analysis, noise (median residual), level sweep, luminance gradient, bit planes, and copy-move clone detection (plane-corrected block features, edge-like blocks skipped, one color per shift). Side panels: findings, EXIF and GPS, software traces, the EXIF thumbnail beside the picture with their difference, both quantization tables, the coefficient histogram behind the double-compression score, the LSB test curve, JPEG segments and PNG chunks.
  - Region bookmarks: drag a rectangle in any view to bookmark it with tags and a note; the region and view are stored with the bookmark (and its file hash), drawn on the picture, listed on the Bookmarks page and in the bookmark report, and the bookmark reopens the viewer zoomed on the region.
  - "Analyze picture" in the file drawer and on carved pictures; `kokino image <file>` prints the analysis of one exported picture as JSON.
  - API: `GET/POST /api/cases/{cid}/evidence/{eid}/photos`, `GET .../fs/{fi}/file/{idx}/photo`, `GET .../fs/{fi}/file/{idx}/image` (raster formats only, by content, nosniff), `GET .../carved/{id}/photo`; bookmarks take `region` and `view`.
  - Test data: `scripts/make_photo_fixture.py` builds `tests/fixtures/photo/` with one picture per finding and a test of every expected result.
- FAT12, FAT16, FAT32 and exFAT (USB sticks, SD cards, camera cards), through a new `kokino-fat` crate:
  - Every view works on them: Summary, Explorer, Timeline, signatures, full-text search (files, deleted files and free clusters), carving of free clusters, bookmarks, exports and the HTML report. A disk can mix NTFS and FAT partitions.
  - Deleted files and folders: entries marked deleted are listed with name, size, times and first cluster. Long names of deleted files are restored by recovering the lost first byte from the long-name checksum (8.3-only names show it as "?"). Files inside a deleted folder are listed as deleted too. exFAT deleted entry sets are read the same way.
  - Deleted content is read as contiguous clusters from the first one (the FAT chain is cleared on delete); the drawer says "Recovered as contiguous". Clusters that are in use again are reported on the file, and so is a deleted file whose first cluster no longer starts with the header its type needs (a .jpg without a JPEG header), which is common on cameras; the carved files then hold the pictures.
  - Live files follow the FAT chain (fragmented files are read correctly); exFAT files flagged as contiguous (NoFatChain) and the allocation bitmap are honored.
  - FAT times are shown as stored (the device's local time, no time zone, 2 s precision; access is a date only) and the impact summary says so; exFAT times use their stored UTC offset. The FAT type is taken from the boot sector layout and cluster count, not from its type text, and the volume is labeled with what the parser found.
  - The "implausible timestamp" indicator only counts future times on FAT volumes, whose dates start in 1980.
  - Analysis schema 4. Evidence analyzed before needs Re-analyze for its FAT volumes to show.
  - Test data: `scripts/make_fat_fixture.py` builds `fat12.img`, `fat16.img`, `fat32.img`, `exfat.img` and `disk-fat.img` (FAT32 and exFAT partitions) with a fragmented file, deleted files with free and with reused clusters, and a deleted folder. Checked against 7-Zip's FAT reader, and on a public Canon SD card image (NPS 2009 canon2-gen6: FAT12, 33 live photos, 3 deleted ones whose first clusters were overwritten and flagged, 5 JPEGs carved from free clusters).

The deletion is written to the case audit log before the move and to the system audit log with the evidence list and SHA-256 hashes. API: `DELETE /api/cases/{cid}` with `{"confirm": "<case name>"}`.
- Bookmarks and tags:

Tags come from a suggested set (Evidence, Relevant, Suspicious, Exculpatory, Follow up, Privileged, Not relevant) or are typed in; each bookmark has a note.
  - Bookmarks keep a snapshot of their target; for files the server computes MD5 and SHA-256 of the content at bookmark time. Stored per case in `bookmarks.json` (written atomically).
  - New Bookmarks page per case: filter by tag or text, open the item (files reopen by MFT record, so bookmarks survive re-analysis), edit or remove. The menu shows the count.
  - HTML report of bookmarked items, all or one tag, with location, time, hashes, tags, notes and who bookmarked each item.
  - Reviewers can add bookmarks and change or remove their own; examiners and admins manage all. Adds, changes, removals and reports are written to the case audit log.

- File carving (new Carved files page per evidence item):
  - Scans every 512-byte boundary of free NTFS clusters, the space outside partitions and unparsed volumes. Each format has its own end detection, so carved files are whole files and lookalike headers are rejected: JPEG (segment walk), PNG (chunks), GIF (blocks), BMP, WebP/WAV/AVI (RIFF size), PDF (last %%EOF, following incremental updates), ZIP and everything built on it (central directory must point back at the start; DOCX/XLSX/PPTX/ODF/EPUB/JAR/APK told apart by their entries), OLE (DOC/XLS/PPT/MSG/Jump Lists, size from the FAT), SQLite (page count, only when the header confirms it), PE (section table and signature; EXE/DLL/driver, CPU, signed), GZIP (deflate stream end), 7-Zip, MP4/MOV (top-level boxes) and 64 KiB event log chunks (with record count, time range and log name).
  - A file whose end is missing is kept as incomplete; one that runs past its free region is marked; one that starts where a deleted file's data started names that file.
  - Results store offsets, lengths, MD5 and SHA-256, never copies (`<case>/carved/<eid>.json`). Carving runs after analysis automatically, or on demand (examiners and admins); runs and exports are written to the audit log, and each export is checked against the carved hash.
  - Picture gallery (served as images only, with nosniff), a table with links to the hex view, and a detail view with export.
  - Text inside carved PDFs and Office files is decoded into the search index; such hits show as Carved and open the carved file.
  - API: `GET/POST /api/cases/{cid}/evidence/{eid}/carved`, `GET .../carved/{id}/preview`, `GET .../carved/{id}/export`.
  - Test data: `scripts/fixture_carve.py` makes one valid sample per format (including a real baseline JPEG encoder) plus lookalikes; `disk-win.img` carries them, and a test checks every expected result exactly.
- Windows system artifacts and a new System summary page per evidence item:
  - Registry hive reader (all subkey list kinds, big data values, dirty-hive detection): SYSTEM (computer name, time zone, last shutdown, USB storage devices with serial, drive letter and first / last / removal times, network interfaces, services, ShimCache for Windows 8.1-11), SOFTWARE (Windows version, build and install date, owner, user profiles, networks with first / last connection and gateway MAC, installed programs, Run keys), SAM (accounts with RID, last logon, logon count, disabled), NTUSER.DAT per user (UserAssist with run count and focus time, RecentDocs, typed paths, Run box, Explorer searches, Run keys) and Amcache.hve (path, SHA-1, first seen).
  - EVTX reader for the template-based binary XML Windows writes, chunk by chunk so a damaged chunk only loses its own records. Checked against `wevtutil` on 93,000 real records with no errors and identical event IDs, providers, times and record numbers. Notable events are summarized in plain language: log clearing (1102, 104), logons and failed logons with type and source address, privilege use, process creation (4688), account and group changes, services, scheduled tasks, boots and shutdowns, remote desktop, PowerShell script blocks, Defender detections, Wi-Fi connections. Routine machine-account logons are left out of the list but counted.
  - Prefetch reader for versions 17, 23, 26 and 30 (XP to Windows 11), including the "MAM" compressed files of Windows 8.1+ through a new LZXPRESS Huffman decompressor that matches Windows' own compressor byte for byte.
  - Shortcut (LNK) reader: target (local, network share, shell items or URI), target times and size, volume label, serial and drive type, machine name and MAC address from the tracker block. OLE compound file reader. Jump Lists (automatic with DestList entries paired to their shortcuts, custom, and leftover temporary copies).
  - The System summary has Overview, Programs run, Files and folders, USB and networks, Accounts and logons, Events, Software and autostart, and Sources (every artifact file read, with errors and notes). Rows open the artifact file; events open with every field.
  - Windows records join the Timeline (new Windows filter: program runs, files opened, USB, installs, networks, notable events), the impact summary and the HTML report (Windows system section).
  - Two new anti-forensics indicators (18 in total): `log_cleared_event` (Windows recorded a log clearing, with account and time) and `tool_execution_record` (UserAssist, Amcache or 4688 shows a wiping tool ran).
  - `kokino artifact <file> [--full]` parses one exported hive, event log, Prefetch file, shortcut or Jump List and prints JSON.
  - Analysis schema 3. Evidence analyzed before needs Re-analyze for the System summary.
  - Test data: `scripts/fixture_windows.py` and `scripts/make_win_fixture.py` build `tests/fixtures/disk-win.img`, an invented LAB-PC whose artifacts tell one consistent story, with an end-to-end test of every finding.
- Full-text search (new Search tab per evidence item):
  - The index covers every data stream of live and deleted files (deleted content as long as the record still maps it), every cluster marked free in $Bitmap, and the space outside partitions and unparsed volumes. Text is extracted as UTF-8 and UTF-16LE strings of 4 or more characters; Latin, Greek and Cyrillic are kept, and binary noise read as UTF-16 is filtered out.
  - Stored as SQLite FTS5 in `<case>/index/<eid>.sqlite`. Every hit maps back to its offset in the file and in the image, so a click opens the file or the exact byte in the hex view.
  - Modes: keywords (whole words, "phrases", OR, NOT, prefix*; punctuation-safe, so addresses and paths work as typed), regular expressions, and presets for email addresses, URLs, IPv4 addresses, payment cards (Luhn-checked), IBANs (checksum-checked) and Bitcoin addresses. Scope: all, live files, deleted files or unallocated.
  - The index is built automatically after analysis, or on demand with Build / Rebuild index (examiners and admins). Builds and every search (query, scope, hit count) are written to the case audit log.
  - API: `GET/POST /api/cases/{cid}/evidence/{eid}/textindex`, `GET .../textsearch`.
- Text inside documents is indexed too:
  - ZIP and formats built on it (DOCX, XLSX, PPTX and macro variants, OpenDocument, EPUB, JAR...): every entry is inflated; XML parts become plain text (words split by formatting are joined, tracked deletions and comments kept, package plumbing such as styles and themes skipped); nested archives are opened up to 4 levels; damaged or carved ZIPs without a central directory are read from their local headers; ZIP64 is supported.
  - PDF: objects are found by scanning, so damaged and incrementally updated files work; Flate streams and object streams are decoded; page text uses each font's ToUnicode map (CID fonts as made by Word and browsers); document info and XMP metadata are kept.
  - GZIP is decompressed and searched.
  - Hits show where inside the file they are ("inside word/document.xml", "inside page 3") and are marked Decoded; they have no image offset.
  - Decoding is bounded (64 MiB per part, 256 MiB per document, 20,000 entries, 4 levels), so zip bombs cannot exhaust memory. Encrypted entries and PDFs, unsupported compression and cut-off parts are listed on the Search page.
  - Keyword hits that are only spaces or punctuation apart are shown as one match.
  - The index format changed (schema 2): indexes built before this change are reported as outdated and need Rebuild index.

### Security
- Parser bugs found by fuzzing and fixed (crafted evidence could stop or slow a job or exhaust memory; none allowed code execution or wrote to evidence):
  - NTFS: the declared MFT size was trusted (hang, runaway memory); a data-run iterator that repeats its error looped for ever; a boot sector shorter than 512 bytes made the `ntfs` crate panic; read buffers and the free-space bitmap were sized by declared lengths.
  - FAT and exFAT: the boot sector's cluster count sized the in-memory FAT (16 GB from a 2.6 MB image); exFAT sector and cluster shifts were not checked (clusters up to 128 GiB); three unchecked multiplications.
  - Jump Lists (OLE compound files): repeated DIFAT sectors and looping chains (over 500 MiB from a 3 KB file).
  - Registry: a key listed under itself made the tree walk exponential.
  - E01: unchecked chunk geometry arithmetic.
  - JPEG: DC size from the file's Huffman table not checked, coefficient overflow, a frame header claiming 1.2 gigapixels kept the decoder busy on padding (now stops 1 KiB past the data), and a scan naming a component a later frame header removed crashed it.
  - PDF text extraction and PDF carving: two slicing panics.
- Browser history: SQLite databases from evidence are opened in defensive mode with `trusted_schema=OFF`, cell size checks, no memory mapping and a time limit; a database that defines `urls` (or another table Kokino reads) as a view is refused. A crafted History file could otherwise hang the ingest for ever (proof of concept made). Hash set imports from SQLite get the same protection.
- Evidence paths inside the cases directory are refused: an examiner could otherwise add another case's files, the account file or the TLS key as "evidence" and read it in the hex view.
- A panic in a background job now ends the job as failed (with a request to report it) instead of leaving it "running" and blocking Delete case.
- Reports (HTML from the API) are served with a sandboxing Content-Security-Policy and no scripts.
- `#![forbid(unsafe_code)]` in every Kokino crate: the compiler now refuses unsafe Rust anywhere in the product.
